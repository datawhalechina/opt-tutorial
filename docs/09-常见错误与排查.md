# 第 9 章 常见错误与排查

这一章是本仓库重构时**真实踩过**的坑，全部有代码验证。看完能省掉你半天。

## 9.1 参数传错位置：最隐蔽的一类

### COPT 的 `addConstr` 第二个位置参数不是 `name`

```python
# ❌ 名字被静默丢弃，导出 LP 一看变成 R0、R1
model.addConstr(2 * a + 4 * b <= 100, "Production_Time")

# ✅
model.addConstr(2 * a + 4 * b <= 100, name="Production_Time")
```

原因：COPT 的签名是

```python
addConstr(self, lhs, sense=None, rhs=None, name="")
```

第二个位置参数是 **sense**，你传一个字符串进去它照收不误，但不生效。Gurobi 的签名是 `addConstr(self, lhs, name="")`，第二个位置**就是** name —— 所以"照着 Gurobi 抄"必然中招。

验证方法：`model.write("x.lp")` 导出来看一眼约束名。

### 同类问题

| 求解器 | 坑 | 正确写法 |
| :--- | :--- | :--- |
| COPT | `addVars` 用 `name=` | 批量建变量要 `nameprefix=` |
| Gurobi | `addVars` 用 `nameprefix=` | 要 `name=` |
| PuLP | `model += expr` 漏了逗号 | 带名字的约束要 `model += expr, "c1"` |

## 9.2 API 根本不存在，或已经被删了

### `cp.read()` 不存在

```python
# ❌ AttributeError: module 'coptpy' has no attribute 'read'
model = cp.read("m.mps")

# ✅ 先有环境、有模型，再读
env = cp.Envr()
model = env.createModel("m")
model.read("m.mps")
```

### `GRB.SUBOPTIMAL` 在 Gurobi 12 之后被移除

老代码常见的写法：

```python
# ❌ AttributeError: module 'gurobipy' has no attribute 'SUBOPTIMAL'
if model.Status in (GRB.OPTIMAL, GRB.SUBOPTIMAL):
    model.write("solution.sol")
```

改成判断"有没有解"就行：

```python
# ✅
if model.SolCount > 0:
    model.write("solution.mst")
```

### `Model.write` 不是 docplex 的方法

```python
# ❌ AttributeError
model.write("m.lp")

# ✅
model.export_as_lp("m.lp")
model.export_as_mps("m.mps")
```

docplex 也没有 `Model.from_file`，读模型要用 `ModelReader`：

```python
from docplex.mp.model_reader import ModelReader
model = ModelReader().read("m.lp")
```

## 9.3 文件格式的想当然

### `.sol` 读不回来

```python
# ❌ gp.read 只认 .lp/.mps/.rew/.rlp
model = gp.read("solution.sol")
```

Gurobi 的 `read()` 官方说明只接受 `.lp`、`.mps`、`.rew`、`.rlp`；`Model.read()` 只接受 `.mst`、`.bas`、`.prm`。`.sol` 是老式**只写**格式。

要交换解，用 `.mst`（MIP start）或 `.json`。

### `.ilp` 不是"IIS 专用格式"

`.ilp` 本质是 LP 语法 + 整数变量声明。Gurobi 把 IIS 写成 `.ilp`，是因为 IIS 就是"一组 LP 约束"，不是因为它俩是同一个东西。

## 9.4 求解器之间的能力差异

### HiGHS 不支持指示约束

```python
# ❌ HiGHS 没有 addGenConstrIndicator / addConsIndicator
model.addGenConstrIndicator(y, 1, expr >= 8)

# ✅ 用两条 big-M 线性约束替代
model.addConstr(expr - 20 * y <= 0, "capacity")
model.addConstr(expr - 8 * y >= 0, "min_output")
```

写模型时如果希望"五个求解器都能跑"，**优先用 big-M**，指示约束作为可选优化。

### Pyomo 的 `scip` 后端 ≠ pyscipopt

`SolverFactory("scip")` 调的是 SCIP 的 ASL 命令行程序，装了 `pip install pyscipopt` 不会让它可用。要用 PySCIPOpt 就直接 `from pyscipopt import Model`。

## 9.5 日志与状态误读

### `Bounds range [0e+00,0e+00]` 不是"无界"

```
Range of bound coefficients: [0e+00,0e+00]
```

意思是"所有变量的上下界都为 0"，通常说明界已经被收进约束里了。无界（unbounded）是求解**状态**，不是这个数字。

### 状态码语义

| 现象 | Gurobi | COPT | HiGHS | 含义 |
| :--- | :--- | :--- | :--- | :--- |
| 最优 | `Status == 2` | `status == 1` | `kOptimal` | 求出最优解 |
| 不可行 | `Status == 3` | `status == 2` | `kInfeasible` | 没有可行解，先查 IIS |
| 无界 | `Status == 5` | `status == 3` | `kUnbounded` | 目标可以无限好，通常是漏了约束 |
| 到时限 | `Status == 9` | `status == 8`（`COPT.TIMEOUT`） | `kTimeLimit` | 有解但不保证最优，看 Gap |

直接拿 `ObjVal` 前**一定先判状态**，否则在不可行/到时限时会拿到一个没意义的数或者直接抛异常。

## 9.6 建模层面的错

| 错误 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 0-1 背包写成"件数"整数变量 | 解出来是另一个问题的最优 | 明确 `vtype` 是 binary 还是 integer |
| big-M 填 `1e9` | LP 松弛极弱，节点数爆炸，求解器之间结果不一致 | 用问题自身的上界 |
| 用 `==` 表达"约等于" | 永远不可行 | 改区间约束 |
| 变量不设上界 | 无界解 | 该有界就设界 |
| 忘写非负约束 | 解出负数产量 | 建变量时 `lb=0` |

## 9.7 一套排查流程

模型跑不出预期结果时，按这个顺序查：

1. **先看状态，不要看数值**
   ```python
   print(model.Status)      # 是 2/OPTIMAL 吗？
   ```
2. **不可行 → 算 IIS**（第 5 章 5.5 节），看是哪几条约束打架
3. **导出 LP 文件肉眼过一遍**
   ```python
   model.write("debug.lp")
   ```
   重点看：约束名对不对、系数有没有搞反、big-M 是不是大得离谱
4. **缩小规模**：把数据砍到 2×2 手算一遍，和求解器结果比
5. **换一个求解器验证**：同一个模型用 HiGHS 再跑一遍
   ```bash
   python scripts/verify_all.py
   ```
   两个求解器给出不同最优值 → 模型（不是求解器）有问题

## 9.8 版本漂移：为什么要有一键校验

本仓库原版写于 2024 年，基于 Gurobi 9.5 / COPT 7.1.4。两年后：

- Gurobi 删掉了 `GRB.SUBOPTIMAL`
- COPT 的 `addConstr` 签名依旧但名字参数位置早已不同（Gurobi 风格照抄必错）
- HiGHS 的 Python 接口从"passModel + 矩阵"演进到 `addVariable` 代数式写法

**API 会变，教程会过期，只有能跑的测试不会骗人。** 所以本仓库每个例题配了 3~5 个求解器实现，外加 `scripts/verify_all.py`：只要有求解器升级导致行为变化，跑一次就知道。

CI 里只跑开源求解器（HiGHS / SCIP / CBC），因为它们不需要 license；商用求解器的正确性靠贡献者本地验证 + PR 时贴 `verify_all.py` 的输出。
