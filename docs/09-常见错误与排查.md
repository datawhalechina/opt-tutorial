# 第 9 章 常见错误与排查

这一章是本仓库重构时**真实踩过**的坑，每条都能用代码复现。看完能省掉你半天。

## 9.1 参数传错位置：最隐蔽的一类

### COPT 的 `addConstr` 第二个位置参数不是 `name`

```python
# ❌ 名字被静默丢弃，导出 LP 一看变成 R0、R1
model.addConstr(2 * a + 4 * b <= 100, "Production_Time")

# ✅
model.addConstr(2 * a + 4 * b <= 100, name="Production_Time")
```

原因在于两家 `addConstr` 的签名不同：

```python
Gurobi:  addConstr(self, lhs, name="")
COPT:    addConstr(self, lhs, sense=None, rhs=None, name="")
```

**COPT 的 `sense` 是「约束关系符」**，取值 `'L'` / `'G'` / `'E'`（即 `COPT.LESS_EQUAL` / `GREATER_EQUAL` / `EQUAL`），只在三段式写法里用到：

```python
# 等价的两种写法
model.addConstr(x + y <= 4, name="c0")
model.addConstr(x + y, COPT.LESS_EQUAL, 4, name="c0")   # sense='L'
```

注意它和 `setObjective(expr, sense=COPT.MAXIMIZE)` 里那个表示**目标方向**的 `sense` 是两回事，只是参数名撞了。

于是 `addConstr(完整约束, "名字")` 会把名字塞进 `sense`：因为 `lhs` 已经是成形约束、`rhs` 为空，这一路**不校验也不使用** `sense`，字符串被直接忽略，约束名丢失并自动命名成 `R0`。

只有当真的给了 `rhs`（三段式）时才会校验，那时才会报错：

```python
model.addConstr(x, "Production_Time", 100)   # ValueError: Unsupported constraint sense
```

所以这个坑**不会报错**，只能靠导出 LP 或 `getConstrs()` 看名字才发现。

Gurobi 那边第二个位置**就是** name，所以"照着 Gurobi 抄"必然中招。这是两家接口的固有差异，不是版本问题。

> 实测对照（COPT 8.0.1，导 LP 看约束名）：
>
> | 写法 | 导出结果 |
> | :--- | :--- |
> | `addConstr(x + y <= 4, name="Production_Time")` | `Production_Time: x + y <= 4` |
> | `addConstr(x + y <= 4, "Production_Time")` | `R0: x + y <= 4` |

验证方法：`model.write("x.lp")` 导出来看一眼约束名。

### 同类问题

| 求解器 | 坑 | 正确写法 |
| :--- | :--- | :--- |
| COPT | `addConstr(expr, "名字")` | 第 2 位是 `sense`，要写 `name=` |
| COPT | `addConstrs(gen, "前缀")` | 第 2 位是 `nameprefix`（默认 `'R'`），名字会拼成 `前缀(0)` |
| COPT | `addVars(n, name="x")` | 批量建变量要 `nameprefix=` |
| Gurobi | `addVars(n, nameprefix="x")` | 要 `name=` |
| PuLP | 以为 `, "名字"` 决定了是约束 | 判定看比较符；`, "名字"` 只是命名 |

## 9.2 API 不存在，或者语义和你想的不一样

### `cp.read()` 不存在

```python
# ❌ AttributeError: module 'coptpy' has no attribute 'read'
model = cp.read("m.mps")

# ✅ 先有环境、有模型，再读
env = cp.Envr()
model = env.createModel("m")
model.read("m.mps")
```

### docplex 的几个"以为有但没有"

| 你以为 | 实际 |
| :--- | :--- |
| `model.write("m.lp")` | ❌ 没有；用 `model.export_as_lp("m.lp")` |
| `model.export_prm("p.prm")` | ❌ 没有；用 `model.export_parameters_as_prm("p.prm")` |
| `Model.from_file("m.lp")` | ❌ 没有；用 `ModelReader().read("m.lp")`（需 CPLEX 运行时） |
| `model.export_as_mps("m.mps")` | ✅ 有，但**需要 CPLEX 运行时**；没运行时只能导 `.lp` |

### HiGHS 的 `maximize()` 会立刻求解

这是最容易在教程里写错的一条：`maximize()` / `minimize()` **不是**"只设目标"，内部直接调了 `solve()`。

```python
# ❌ 这行等于先用残缺模型求了一次解（日志里会多一段 Unbounded）
model.maximize(40 * a + 50 * b)
model.addConstr(2 * a + 4 * b <= 100, "Production_Time")
model.run()

# ✅ 只设目标，最后统一 run()
model.setObjective(40 * a + 50 * b, highspy.ObjSense.kMaximize)
model.addConstr(2 * a + 4 * b <= 100, "Production_Time")
model.run()
```

### Pyomo 里名字写错不会报错

```python
s = pyo.SolverFactory("copt_direct")     # 6.10.1 里根本没这个后端
print(type(s).__name__)                  # UnknownSolver —— 不抛异常
print(s.available(exception_flag=False)) # False
```

`copt_direct`、`appsi_scip` 这类名字在 Pyomo 6.10 里都不存在（COPT 请走 `pulp.COPT` 或原生 `coptpy`）。**调 `solve()` 前一定先 `available()` 探测。**

## 9.3 文件格式的想当然

### `.sol` 能读，但不是用 `gp.read()`

```python
# ❌ gp.read 只建模型，读不了任何解文件
model = gp.read("solution.sol")

# ✅ 读解要用 Model.read()
model = gp.read("m.lp")
model.read("solution.sol")     # 当作 MIP start 导入
```

Gurobi 官方把 SOL / JSON / MST / BAS 都归为 "Solution File Formats"，明确说"all solution file formats can be used to import solution information"。所以 `.sol` 不是"只写"，只是**读取入口不同**。

### `.mst` 不含连续变量的值

写 `.mst` 时 Gurobi 只保存整数变量的值（它的用途是给 MIP 提供 start）。如果模型有连续变量（本仓库的设施选址、排程、CVRP 都是），拿 `.mst` 交换解会丢数据。**完整解用 `.sol` 或 `.json`。**

### `.json` 是解，不是模型

`.json` 存的是变量值 + 求解统计（Status / ObjVal / 节点数），不含模型，也不能当起始解读回来。想交换模型用 `.lp` / `.mps`。

### `.ilp` 就是 IIS 专用格式

官方原文：*This format is identical to the LP format but it is used for Irreducible Inconsistent Subsystem (IIS) models.* 语法和 `.lp` 一样，用途专一。COPT 的 IIS 后缀是 `.iis`——写 `.ilp` 不报错，但**不生成文件**。

## 9.4 求解器之间的能力差异

### HiGHS 不支持指示约束

```python
# ❌ HiGHS 没有 addGenConstrIndicator / addConsIndicator
model.addGenConstrIndicator(y, 1, expr >= 8)

# ✅ 用两条线性约束替代（前提：expr >= 0）
model.addConstr(expr - 20 * y <= 0, "capacity")
model.addConstr(expr - 8 * y >= 0, "min_output")
```

写模型时如果希望"五个求解器都能跑"，**优先用 big-M**，指示约束作为可选优化。

### PuLP 没有指示约束，也没有懒约束

两样都没有接口，换后端也不会突然可用。需要它们就回原生 API。

### Pyomo 的 `scip` 后端 ≠ pyscipopt

`SolverFactory("scip")` 调的是 SCIP 的 ASL 命令行程序，装了 `pip install pyscipopt` 不会让它可用。要用 PySCIPOpt 就直接 `from pyscipopt import Model`。

## 9.5 日志与状态误读

### `Bounds range [0e+00,0e+00]` 不是"无界"

```
Range of bound coefficients: [0e+00,0e+00]
```

这行统计的是变量**有限界**的取值范围，$+\infty$ 不计入。`lb=0` 且没有上界的变量就会显示 `[0,0]`。它既不是"上下界都是 0"，也不是无界——无界是求解状态。

### 状态码语义

| 现象 | Gurobi | COPT | HiGHS | 含义 |
| :--- | :--- | :--- | :--- | :--- |
| 最优 | `Status == 2` | `status == 1` | `kOptimal` | 求出最优解 |
| 不可行 | `Status == 3` | `status == 2` | `kInfeasible` | 没有可行解，先查 IIS |
| 无界 | `Status == 5` | `status == 3` | `kUnbounded` | 目标可以无限好，通常是漏了约束 |
| 不可行或无界 | `Status == 4` | `status == 4` | — | 求解器没区分，Gurobi 需设 `DualReductions=0` 再解一次 |
| 到时限 | `Status == 9` | `status == 8`（`COPT.TIMEOUT`） | `kTimeLimit` | 可能已找到可行解，也可能没有 |

两条纪律：

1. **读目标值之前先判状态**。到时限/无解时 `ObjVal` 可能报错，也可能给出一个没意义的数。
2. **"有解"和"最优"是两件事**。写健壮的代码应该是：

```python
model.optimize()
if model.SolCount == 0:                       # Gurobi：没有可行解
    raise RuntimeError(f"无可行解 Status={model.Status}")
if model.Status != GRB.OPTIMAL:               # 有解但未证最优
    print(f"未证最优（Status={model.Status}），以下为当前最好解")
```

CPLEX 对应 `model.get_solve_status() == JobSolveStatus.OPTIMAL_SOLUTION`；COPT 可以看 `model.hasmipsol`；HiGHS 看 `getModelStatus()`。

## 9.6 建模层面的错

| 错误 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 0-1 背包写成"件数"整数变量 | 解出来是另一个问题的最优 | 明确 `vtype` 是 binary 还是 integer |
| big-M 填 `1e9` | LP 松弛极弱，节点数爆炸，求解器之间结果不一致 | 用问题自身的上界 |
| 用 `==` 表达"约等于" | 永远不可行 | 改区间约束 |
| 该有界却不设界 | 无界解的常见原因（不是充分条件：其它约束可能隐含界住） | 该有界就设界 |
| 忘写非负约束 | 解出负数产量 | 建变量时 `lb=0` |
| 对称性约束从 $i=1$ 写起 | $y_i \le \sum_{l<i} y_l$ 会把 $y_1$ 逼成 0 | 从 $i=2$ 开始 |

## 9.7 一套排查流程

模型跑不出预期结果时，按这个顺序查：

1. **先看状态，不要先看数值**
   ```python
   print(model.Status)      # 是 2/OPTIMAL 吗？SolCount 是多少？
   ```
2. **不可行 → 算 IIS**（第 5 章 5.5 节），看是哪几条约束打架
3. **导出 LP 文件肉眼过一遍**
   ```python
   model.write("debug.lp")
   ```
   重点看：约束名对不对、系数有没有搞反、big-M 是不是大得离谱、变量类型对不对
4. **缩小规模**：数据砍到 2×2 手算一遍，和求解器结果比
5. **换一个求解器验证**：同一个模型用 HiGHS 再跑一遍

```bash
python scripts/verify_all.py
```

两个求解器给出不同最优值 → 模型（不是求解器）有问题。

## 9.8 版本漂移：为什么要有一键校验

本仓库原版写于 2024 年，用的是 Gurobi 9.5 / COPT 7.1.7 / HiGHS 早期版本。两年后真实发生的变化：

| 变化 | 影响 |
| :--- | :--- |
| HiGHS 的 Python 接口从"构造 `HighsLp` 矩阵 + `passModel`"演进到 `addVariable` 代数式写法 | 老代码的建模方式在新版里已经不是推荐写法 |
| `highspy` 的 `maximize()` 内部改为立即求解 | 教程里"设目标→加约束→run"的顺序会先解一个空模型 |
| PuLP 3.3 把 `LpVariable(name, ...)` 直接构造标记为 deprecated，4.0 会改为 `prob.add_variable()` | 升级后老写法失效 |
| COPT 的 `addConstr` 第 2 个位置参数一直是约束关系符 `sense` | 与 Gurobi 的 `name` 位置冲突，照抄就丢约束名 |

**API 会变，教程会过期，只有能跑的测试不会骗人。** 所以本仓库每个例题配了 3~5 个求解器实现，外加 `scripts/verify_all.py`：只要有求解器升级导致行为变化，跑一次就知道。

CI 里跑的是免授权的 HiGHS 与 SCIP（PuLP 默认后端也是 HiGHS），商用求解器的正确性靠贡献者本地验证 + PR 时贴 `verify_all.py` 的输出。
