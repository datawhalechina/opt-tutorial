# 第 6 章 解读求解器日志与调参

求解器跑完只给一个数，日志才是"过程证据"：它到底求了多久、卡在哪、离最优还差多远、要不要调参。这一章的日志都是本仓库脚本真实跑出来的——其中**时间列随机器和版本变化**，不必对得一模一样；为了排版也删掉了部分重复行，原文在 `code/ch06_logging/output/`。

## 6.1 求解器大致在做什么

**线性规划**

1. 预处理：统一量纲、删冗余行列、把界收到约束里
2. 选算法：单纯形 or 内点（求解器自动选）
3. 迭代：单纯形沿顶点走，内点从内部逼近
4. 输出：状态、目标值、迭代次数

**混合整数规划**

1. 预处理：探测固定变量、收紧系数、加对称性破除
2. 求 LP 松弛：把整数约束先放开，得到一个下界（最小化问题）
3. 分支定界：对小数变量分支，子问题再求 LP 松弛
4. 割平面 / 启发式：加割收紧松弛，用启发式找可行整数解
5. 收敛：上下界重合（Gap → 0）或触到时限

## 6.2 怎么拿到日志

| 求解器 | 打开/关闭日志 | 写入文件 | 少刷屏 |
| :--- | :--- | :--- | :--- |
| Gurobi | `Params.OutputFlag = 1/0`（0 是总闸，会连文件一起关） | `Params.LogFile = "g.log"` | `Params.DisplayInterval = 60`（默认 5 秒一行） |
| COPT | `setParam("Logging", 1/0)` | `setLogFile("c.log")`（**追加写**） | 同左 |
| CPLEX | `solve(log_output=True/False)` | `solve(log_output="c.log")` | 同左 |
| HiGHS | `setOptionValue("output_flag", True)` / `setOptionValue("log_to_console", False)` | `setOptionValue("log_file", "h.log")`（**追加写**） | `log_to_console=False` |
| SCIP | 默认打印，`setParam("display/verblevel", 0)` 降噪 | `model.setLogfile("s.log")` | `display/verblevel` |

四个容易踩的点：

- **Gurobi 的 `OutputFlag` 是总闸**：设 0 之后再设 `LogFile` 也写不出东西。只想静音屏幕就 `LogToConsole = 0` + `LogFile = "g.log"`。
- **Gurobi 没有"详细程度"档位**，能调的是输出频率 `DisplayInterval`；只有 Compute Server / WLS 场景才有 `CSClientLog` 三档。
- **COPT 官方把 `LogToConsole` 定义为控制台开关，但 8.0.1 实测设 0 不生效**；可靠的是 `Logging = 0`。
- **COPT 与 HiGHS 的日志文件都是追加写**，同一个脚本跑两次，文件里会叠两段。本仓库的脚本在写之前先删旧文件。

逐段看：

| 日志 | 含义 |
| :--- | :--- |
| `Hardware has 8 cores and 8 threads` | 这台机器 8 核 8 线程，求解器最多用 8 线程 |
| `The original problem has 2 rows, 2 columns` | 原模型 2 约束 2 变量 |
| `The presolved problem has …` | 预处理后规模，两者一样说明没删掉东西 |
| `Range of matrix coefficients [1e+00,4e+00]` | 约束系数跨度只有 1~4，数值很健康 |
| `Range of bound coefficients [0e+00,0e+00]` | 变量**有限**界的取值范围。$+\infty$ 不计入统计，所以 `lb=0` 且没有上界的变量就显示 `[0,0]`。它只是数值健康度统计，不是"无界"指示器 |
| `Method = Dual` | 用的是对偶单纯形 |
| `Iteration 0 → 2` | 迭代 2 次收敛；第 0 次有 2 个原始不可行（Primal.NInf=2），第 2 次降为 0 |
| `Status: Optimal` | 已求到最优 |

> 判断数值是否健康，看 `Range of ... coefficients` 的最值和跨度。跨度到 $10^8$ 以上就要考虑统一量纲了。

```
     Nodes    Active  LPit/n  IntInf     BestBound  BestSolution     Gap   Time
         0         1      --       0  0.000000e+00            --     Inf  0.10s
H        0         1      --       0  0.000000e+00  3.080000e+02 100.00%  0.10s
         0         1      --       3  2.202222e+02  3.080000e+02  28.50%  0.10s
H        0         1      --       3  2.202222e+02  2.780000e+02  20.78%  0.10s
         0         1      --       1  2.702222e+02  2.780000e+02  2.798%  0.11s
*        0         1      --       0  2.730000e+02  2.730000e+02  0.000%  0.12s
         1         0     3.0       0  2.730000e+02  2.730000e+02  0.000%  0.12s

Best solution   : 273.000000000
Best bound      : 273.000000000
Best gap        : 0.0000%
```

| 列 / 标记 | 含义 |
| :--- | :--- |
| `Nodes` | 已处理的节点数。一直为 0 说明还在根节点（在加割、跑启发式） |
| `Active` | 待处理的节点数（分支定界树的宽度） |
| `LPit/n` | 平均每个节点的单纯形迭代次数 |
| `IntInf` | 当前 LP 松弛解里"还没取整"的整数变量个数 |
| `BestBound` | 当前最优下界（最小化问题），由未处理节点的松弛解给出 |
| `BestSolution`（Gurobi 里叫 `Incumbent`） | 当前找到的最好可行整数解 |
| `Gap` | 上下界的相对差距，见下面公式 |
| `H` | 这个可行解是**启发式**找到的 |
| `*` | 这个可行解是**分支**找到的 |

日志讲的故事很清晰：

1. 第 0 行：根节点松弛给出下界 0（还没解 LP 松弛），Gap 无穷
2. `H`：启发式找到一个可行解 308
3. 松弛解算出来了：下界 220.2，Gap 28.5%，IntInf=3（3 个 0-1 变量还是小数）
4. 又一个 `H`：更好的可行解 278
5. 加割后下界抬到 270.2，Gap 只剩 2.8%
6. `*`：分支找到 273，下界也到 273，Gap = 0 → 收工

HiGHS 的同一道题，日志格式不同但信息等价：

```
        Nodes      |    B&B Tree     |            Objective Bounds              |  ...
Src  Proc. InQueue |  Leaves   Expl. | BestBound       BestSol              Gap |
 J       0       0         0   0.00%   -inf            273                Large
         0       0         0   0.00%   220.2222222     273               19.33%
         1       0         1 100.00%   273             273                0.00%
```

`Src` 列是"这个解怎么来的"：`J` 可行性跳跃（feasibility jump）启发式、`B` 分支、`S` 解 LP、`T` 评估节点、`R` 随机舍入……比 Gurobi/COPT 的 `H`/`*` 两分法更细。为便于对照，上面只保留了到 `Gap` 的列，真实输出右侧还有 `Cuts / InLp / Confl. / LpIters / Time` 五列。

## 6.5 Gap 公式与三个常见现象

最小化问题：

$$
\text{Gap} = \frac{\text{Incumbent} - \text{BestBound}}{|\text{Incumbent}|} \times 100\%
$$

这是 Gurobi / HiGHS 的口径。COPT 官方定义略有不同：$\text{RelGap} = |\text{primal} - \text{dual}| / \max(|\text{primal}|, |\text{dual}|)$。可行解为正数时两者数值一致（本节例题都是这种情形），但别把它当唯一公式。

| 现象 | 说明 | 该做什么 |
| :--- | :--- | :--- |
| `Nodes` 长时间为 0，`Time` 在涨 | 还在根节点：加割、跑启发式、试多种分支规则 | 正常，再等等；根节点做完通常 Gap 会大幅下降 |
| Gap 已到阈值但求解不结束 | 某个启发式还在算，或正在补最后一个对偶界 | 通常几十毫秒内结束；真卡住就设 `TimeLimit` |
| `Gap` 一直是 `Large` / `Inf`，`BestBound` 不动 | 找不到可行解（不是没有，是难找） | 给 MIP start、放宽 `MIPGap`、检查 big-M |
| `Primal.NInf` 一直非 0 | 当前解违反约束 | LP 阶段就是不可行，先用 IIS 查冲突 |

## 6.6 常用参数速查

| 目的 | Gurobi | COPT | HiGHS | SCIP |
| :--- | :--- | :--- | :--- | :--- |
| 时限（秒） | `Params.TimeLimit` | `setParam("TimeLimit", s)` | `setOptionValue("time_limit", s)` | `setParam("limits/time", s)` |
| 相对 Gap | `Params.MIPGap` | `setParam("RelGap", g)` | `setOptionValue("mip_rel_gap", g)` | `setParam("limits/gap", g)` |
| 线程数 | `Params.Threads` | `setParam("Threads", n)` | `setOptionValue("threads", n)` | `setParam("lp/threads", n)` |
| 随机种子 | `Params.Seed` | 8.0.1 无此参数 | `setOptionValue("random_seed", n)` | `setParam("randomization/randomseedshift", n)` |
| 算法选择 | `Params.Method` | `setParam("LpMethod", …)` | `setOptionValue("solver", "simplex"/"ipm")` | `setParam("lp/initalgorithm", …)` |

调参优先级建议：**先改模型，再改参数**。同样的题，能靠收紧 big-M、去掉对称性、加有效不等式解决 90% 的性能问题；参数只能在剩余 10% 里做微调。

## 6.7 一个真实的坑：HiGHS 的 maximize() 会立刻求解

HiGHS 的 `maximize()` / `minimize()` **不是"只设目标"**，它们内部直接调用了 `solve()`。所以"先设目标、再加约束"的顺序，等于先用残缺模型求了一次解：

```python
model = highspy.Highs()
a = model.addVariable(lb=0, name="A")
b = model.addVariable(lb=0, name="B")
model.maximize(40 * a + 50 * b)      # ← 这里已经求解了一次：此时没有任何约束
model.addConstr(2 * a + 4 * b <= 100, "Production_Time")   # 约束加晚了
```

实测这一步之后状态是 `kUnbounded`、目标值 0，日志里也会多出一段"空模型求解"的记录。正确写法是只设目标、最后统一 `run()`：

```python
model.setObjective(40 * a + 50 * b, highspy.ObjSense.kMaximize)
model.addConstr(2 * a + 4 * b <= 100, "Production_Time")
model.addConstr(3 * a + b <= 50, "Raw_Material")
model.run()
```

`setObjective` 之后、`run()` 之前，状态是 `kNotset`，不会求解。本仓库所有 HiGHS 示例都按这个写法。

> 顺带记两个格式细节：HiGHS 的 `log_file` 与 COPT 的 `setLogFile` 都是**追加**写；`output_flag=False` 会把日志文件也变成空文件，只想静音屏幕请用 `log_to_console=False`。
