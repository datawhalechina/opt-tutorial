# 第 10 章 模型不可行时的排查（IIS 与可行性松弛）

第 9 章 9.7 节的排查流程里第 2 步写着"不可行 → 算 IIS"，第 5 章 5.5 节给了四家求解器各一行调用。这一章把那一行展开：**IIS 到底给了你什么、它没告诉你什么、以及"最少改多少就能解"该怎么算**。

所有结论都来自本机实跑（COPT 8.0.1 / HiGHS 1.16.0 / PySCIPOpt 6.3.0），Gurobi 与 CPLEX 部分只有函数签名和官方文档，会逐处标注。

## 10.1 为什么"无解"最难查

"结果不对"至少有数字可以怀疑：目标值偏大、某个变量取到奇怪的边界、和手算对不上。而"无解"只给你一个状态码。

```
Model status        : Infeasible
```

没有变量值、没有对偶价格、没有违反量。求解器内部其实知道是哪几条约束打架，但它默认不说——因为"冲突"不是唯一的，它也不知道你想听哪个版本。

于是排查分成三条主线，各自回答不同的问题：

| 主线 | 回答的问题 | 产出 | 代价 |
| :--- | :--- | :--- | :--- |
| **建模自查** | 是不是我写错了？ | 一个人肉发现的笔误 | 最便宜，先做 |
| **IIS**（不可约不一致子系统） | 哪几条约束在打架？ | 一个最小冲突集（可能有好几个） | LP 很快；MIP 可能很贵 |
| **可行性松弛**（feasRelax / 弹性模型） | 最少改多少就可行？ | 每条约束被改了多少 + 总代价 | 要多解一个模型 |

三者的关系不是"选一个"，而是"从便宜到贵依次上"。10.6 节给完整清单。

### 本章统一的不可行例题

两条产线，各自的产能上限和合同交货下限冲突：

$$
\begin{aligned}
\max\quad & 40a + 50b \\
\text{s.t.}\quad
& \text{cap\_A}:\quad a \le 15 \\
& \text{cap\_B}:\quad b \le 5 \\
& \text{order\_A}:\quad a \ge 20 \\
& \text{order\_B}:\quad b \ge 8 \\
& \text{shared}:\quad a + b \le 100 \\
& a, b \ge 0
\end{aligned}
$$

`cap_A` 与 `order_A` 不可能同时成立（$a$ 既要 $\le 15$ 又要 $\ge 20$），`cap_B` 与 `order_B` 同理，而这两组**互不相关**——`shared` 谁都不碰。

所以这个模型里有**两个独立的 IIS**：

| 组 | 包含的约束 | 修法 |
| :--- | :--- | :--- |
| 组 1 | `cap_A` + `order_A` | 订单外协 5 件，或把产线扩到 20 |
| 组 2 | `cap_B` + `order_B` | 订单外协 3 件，或把产线扩到 8 |

这就是实操里最常见的坑：**求解器一次只返回一个 IIS**，你修好它、再跑、又是 infeasible，会以为工具没起作用。

## 10.2 IIS 的概念要讲准

**IIS（Irreducible Inconsistent Subsystem，不可约不一致子系统）**：模型的一个子集，满足两个性质

1. 子集本身仍然不可行；
2. 从子集里去掉**任意一条**约束（或任意一个变量界），剩下的就可行。

"不可约"（irreducible）的分量全在第二条上：单说"不可行"没用——整个模型当然不可行；只按条数最少也不够——必须是"去掉其中任意一条就可行"。

三个最容易想歪的地方：

### 最小 ≠ 唯一

同一个模型可以有多个 IIS，每个都合法。10.1 节的例题里，本机三家的结果：

| 求解器 | 返回的 IIS |
| :--- | :--- |
| COPT 8.0.1 | `cap_B` + `order_B` |
| HiGHS 1.16.0 | `cap_B` + `order_B` |
| SCIP（PySCIPOpt 6.3.0） | `cap_A` + `order_A` |

两家给 B 组、一家给 A 组，**都对**。所以"IIS 里没出现某条约束"不等于"这条约束没问题"，换求解器、换参数、甚至只改一下约束顺序都可能换一组答案。

### 一个模型可以有多个独立 IIS，必须循环修

COPT 那一路的实跑（`code/ch10_infeasible/iis_copt.py`）把这个过程走了一遍：

```
第 1 轮：不可行（status=2，COPT.INFEASIBLE=2）
  HasIIS=1 IsMinIIS=1 IISRows=2 IISCols=0
    ★ cap_B    界=[-1e+30, 5] iislb=0 iisub=1
    ★ order_B  界=[8, 1e+30] iislb=1 iisub=0
  修复：order_B 的下限 8 → 5（超出产能的订单外协）

第 2 轮：不可行（status=2，COPT.INFEASIBLE=2）
  HasIIS=1 IsMinIIS=1 IISRows=2 IISCols=0
    ★ cap_A    界=[-1e+30, 15] iislb=0 iisub=1
    ★ order_A  界=[20, 1e+30] iislb=1 iisub=0
  修复：order_A 的下限 20 → 15（超出产能的订单外协）

第 3 轮：已经是可行模型，目标值 = 850
    a = 15
    b = 5
```

注意第 2 轮的 IIS 里根本没有 `cap_B`/`order_B`（已经修了），也没有 `shared`（它从来不参与冲突）。**"不可行 → IIS → 修 → 再解"要一直循环到可行**，不能只做一轮。

### IIS 里可能有变量界，不只是约束

变量上下界也是约束。把 `order_A` 写成 `a` 的下界 `lb=20`，冲突同样存在，只是此时 IIS 成员是一个界而不是一行。COPT 用 `IISRows`/`IISCols` 分别统计，HiGHS 用 `row_index_`/`col_index_` 两组数组分别给。

## 10.3 五家 API 对照

| 求解器 | 算 IIS | 落地文件 | 取冲突内容 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| Gurobi | `model.computeIIS()` | `model.write("c.ilp")` | `IISConstr` / `IISLB` / `IISUB` 属性 | MIP 也能算，但官方明说"可能很贵" |
| COPT | `model.computeIIS()` | `model.writeIIS("c.iis")` | `con.iislb` / `con.iisub`，`IISRows` / `IISCols` | 后缀必须是 `.iis` |
| CPLEX（docplex） | `ConflictRefiner().refine_conflict(model)` | 未验证 | 结果里 `Member` 状态的约束 | **必须有 CPLEX 运行时** |
| HiGHS | `status, iis = model.getIis()` | `model.writeIisModel("iis.lp")` | `iis.row_index_` + `iis.row_status_` | 默认策略会给空结果 |
| SCIP | `iis = model.generateIIS()` | 无（IIS 对象没有写文件方法） | `iis.getSubscip().getConss()` | 结果里带"是否已证不可约" |

同一个"算 IIS"，五家的返回值形状完全不一样：Gurobi/COPT 原地打标记，HiGHS 返回二元组 + 结构体，SCIP 返回一个**带子模型的对象**。下面的代码都是按各家的实际形状写的。

### 10.3.1 Gurobi（本机未实跑：缺许可证）

```python
import gurobipy as gp
from gurobipy import GRB

model.optimize()
if model.Status == GRB.INF_OR_UNBD:          # 4：求解器没区分不可行和无界
    model.Params.DualReductions = 0          # 关掉对偶归约再解一次
    model.optimize()

if model.Status == GRB.INFEASIBLE:           # 3
    model.computeIIS()
    model.write("conflict.ilp")              # .ilp 是 IIS 专用格式，语法同 .lp

    # 两条路等价：批量属性 / 逐个对象
    # flags = model.getAttr("IISConstr", model.getConstrs())
    for con in model.getConstrs():
        if con.IISConstr:
            print("冲突约束：", con.ConstrName)
    for var in model.getVars():
        if var.IISLB or var.IISUB:           # 变量界也能进 IIS
            print("冲突界：", var.VarName)
```

`Model.computeIIS(callback=None, wheres=None)` 和 `IISConstr` / `IISLB` / `IISUB` / `IISMinimal` 这几个属性都在 gurobipy 14.0 里核对过（签名与属性枚举），本机 `License expired 2025-07-02`，所以上面的代码**没有跑过**，只保证 API 名字对得上。

### 10.3.2 COPT（已实跑）

```python
model.solve()
if model.status == COPT.INFEASIBLE:
    model.computeIIS()
    model.writeIIS("conflict.iis")            # 后缀不是 .ilp！
    print(model.getAttr("HasIIS"), model.getAttr("IsMinIIS"),
          model.getAttr("IISRows"), model.getAttr("IISCols"))
    for con in model.getConstrs():
        if con.iislb or con.iisub:            # iislb：下界在冲突里；iisub：上界在冲突里
            print(con.name, con.lb, con.ub)
```

COPT 的 IIS 还带几个有用的属性：

| 属性 | 含义 |
| :--- | :--- |
| `HasIIS` | 是否找到了 IIS |
| `IsMinIIS` | 找到的这个是否已证最小 |
| `IISRows` / `IISCols` | IIS 里的约束条数 / 变量界个数 |

写出来的 `.iis` 文件长这样（第一轮）：

```
Maximize
   50 b
Subject To
 cap_B: b <= 5
 order_B: b >= 8
END
```

`shared`、`cap_A`、`order_A` 全都消失了——IIS 是一个**独立的子模型**，只留冲突成员。这也是它比"打印一堆约束"好用的地方：文件可以直接丢给同事看。

写 `.ilp` 不会报错，但**不会生成文件**（第 5 章 5.5 节已经踩过这个坑，这里再强调一次）。

### 10.3.3 HiGHS（已实跑）

```python
model.run()
status, iis = model.getIis()                  # 返回二元组，不是单个对象
model.setOptionValue("iis_strategy", highspy.IisStrategy.kIisStrategyIrreducible)
status, iis = model.getIis()                  # 换个策略再算一次
model.writeIisModel("iis.lp")
```

实跑输出（`code/ch10_infeasible/iis_highs.py`）：

```
求解状态：Infeasible
默认策略：status=HighsStatus.kOk，rows=0，cols=0
irreducible 策略：rows=2，cols=1
    cap_A    不在冲突里
    cap_B    ★ 在冲突里
    order_A  不在冲突里
    order_B  ★ 在冲突里
    shared   不在冲突里
    列 b     界被放开（free）
写出 output/iis_highs.lp：
    min
     obj:
    st
     cap_B: +1 b <= +5
     order_B: +1 b >= +8
    bounds
     b free
    end
```

**第一个坑：默认策略返回空 IIS。** `iis_strategy` 默认是 `kIisStrategyLight`（0），它只做一次轻量筛选（检查明显不相容的界），对本例这种纯约束型冲突**返回 0 行，而且状态还是 `kOk`**——不报错、不告警，看起来像"模型没问题"。必须显式设成 `kIisStrategyIrreducible`（4，官方示例 `call_highs_from_python.py` 的写法）才拿得到真 IIS。**静默返回空结果比报错危险得多**：报错你会去查文档，空结果你只会以为模型没问题。

**第二个坑：两个数组是并列的，不是下标对应的。**

| 字段 | 长度 | 含义 |
| :--- | :--- | :--- |
| `row_status_` | 全部行数 | 每一行在不在冲突里：`-1` 不在、`0` 可能、`1` 在 |
| `col_status_` | 全部列数 | 同上，按列 |
| `row_index_` / `row_bound_` | IIS 内行数 | 并列数组：第 $k$ 个成员的行号 + 该行保留哪一侧界（2 下界 / 3 上界） |
| `col_index_` / `col_bound_` | IIS 内列数 | 并列数组：列号 + 该列在 IIS 子模型里的界状态（1 = free，界被放开） |

所以 `for j, name in enumerate(lp.row_names_)` 配 `row_status_[j]` 是**对的**，而 `col_bound_[j]` 配第 $j$ 列是**错的**（两者长度不同，会 `IndexError`）。`col_index_` 也不是"哪些变量界进了冲突"，而是"IIS 子模型里保留了哪些列、给了什么界"——上面那份 `.lp` 里 `b free` 就是这么来的。

实跑输出（`code/ch10_infeasible/iis_scip.py`）：


注意它给的是 A 组，和 COPT/HiGHS 的 B 组不同——见 10.2 节"最小 ≠ 唯一"。

### 10.3.5 CPLEX / docplex（本机无运行时，未实跑成功）

docplex **没有**把冲突精化做成 `Model` 的方法。`dir(Model)` 里没有任何 `conflict` 开头的方法，正确的入口是单独的类：

```python
from docplex.mp.conflict_refiner import ConflictRefiner

refiner = ConflictRefiner()
result = refiner.refine_conflict(model)          # 返回 ConflictRefinerResult
for conflict in result.iter_conflicts():
    print(conflict.status, conflict.name)        # status: Member / Possible_member / Excluded
```

底层的等价写法是 `model.get_cplex().conflict.refine(...)`，`model.get_cplex()` 在 docplex 2.32 里确实存在，但它和 `refine_conflict()` 一样要 CPLEX 引擎。

**两条路都需要 CPLEX 运行时。** 本机只装了 docplex（`has_cplex = False`），实跑结果是：

```
has_cplex: False
raised DOcplexException CPLEX runtime not found: cannot run conflict refiner
```

所以这里**故意不给完整示例**——按第 9 章 9.2 节的教训，给一段跑不了的代码只会让人怀疑自己装错了。要用 CPLEX 的冲突精化，先确认 `model.environment.has_cplex` 为 `True`，再照上面三行写。

## 10.4 可行性松弛：改哪最少就可行

IIS 告诉你"这几条在打架"，但没告诉你"该改哪一条、改多少"。可行性松弛（feasibility relaxation）就是把这件事变成一个优化问题：**给每条约束配一个惩罚，求"总惩罚最小"的改动方案**。

### 弹性模型长什么样

原始约束 $a_r^\top x \le b_r$ 改成

$$
a_r^\top x + s_r^{+} - s_r^{-} = b_r,\qquad s_r^{+}, s_r^{-} \ge 0
$$

$s_r^{-}$ 是"从左边减掉多少才满足上界"，也就是违反量；$s_r^{+}$ 用于下界方向。三种关系符的统一读法：

| 原关系符 | 违反量看哪个 | 说明 |
| :--- | :--- | :--- |
| `<=` | $s_r^{-}$ | $a^\top x$ 超过 $b$ 的部分 |
| `>=` | $s_r^{+}$ | $a^\top x$ 不到 $b$ 的部分 |
| `==` | $s_r^{+} + s_r^{-}$ | 两个方向都要算 |

目标函数是加权和：

$$
\min \sum_r w_r \cdot (\text{违反量}_r)
$$

$w_r$ 就是业务语义——"合同违约的代价是产能超发的 10 倍"，直接写进权重。**这一步是整个方法里唯一需要人来决定的地方**，求解器只负责在你给的权重下找最省钱的方案。

### 三种"最少"：L1 / L2 / L0

"最少改动"至少有三种量法，结果往往完全不同：

| 量法 | 目标 | Gurobi `relaxobjtype` | COPT `FeasRelaxMode` |
| :--- | :--- | :---: | :---: |
| L1 违反量之和 | $\sum w_r v_r$ | 0 | 0 |
| L2 违反量平方和 | $\sum w_r v_r^2$ | 1 | 4 |
| L0 违反条数 | $\sum w_r [v_r > 0]$ | 2 | 2 |

COPT 还有 1/3/5 三个 mode，等于"先按上面三种量法把违反量压到最小，再在这个前提下优化原目标"；Gurobi 对应的开关是 `minrelax=True`（见 10.5 节）。

> ⚠️ **这三行数字最容易记错，以本机安装版本的 docstring 为准。** gurobipy 14.0 里 `feasRelaxS.__doc__` 的原文是 `Options are linear (0), quadratic (1), or cardinality (2)`，官方 [Infeasibility Analysis](https://docs.gurobi.com/projects/optimizer/en/current/features/infeasibility.html) 页的三节标题同样是"Sum of Violations / Sum of Squares / Count of Violations"。写代码前用一句 `print(gp.Model.feasRelaxS.__doc__)` 确认，比查博客可靠——"1 是条数、2 是平方和"这种记法在别处流传很广，照着填就会把"条数"当"平方和"用，得到的结果不报错但完全不是你要的意思。

L2 和 L0 的差别在实测里非常直观：L2 会把违反量**摊平**到多条约束上（$2.5^2 \times 2 + 1.5^2 \times 2 = 17 < 5^2 + 3^2 = 34$），L0 加上原目标则会**牺牲某一条约束**——只要违反条数不变（本例 $a$、$b$ 各一条，2 条躲不掉），把 $b$ 顶到 100 也无所谓。

### 10.4.1 Gurobi（本机未实跑：缺许可证）

```python
# feasRelax 是 destructive 的：直接改写当前模型，所以先 copy
relax = model.copy()
relax.feasRelaxS(0, False, False, True)
#                 │  │      │      └── crelax：允许松弛约束
#                 │  │      └───────── vrelax：允许松弛变量界
#                 │  └──────────────── minrelax：是否把最小违反量锁成约束
#                 └─────────────────── relaxobjtype：0=L1 / 1=L2 / 2=L0
relax.optimize()

# Gurobi 自己加的辅助变量就是"违反量"：
#   ArtP_<约束名> / ArtN_<约束名>  约束的正/负松弛
#   ArtL_<变量名> / ArtU_<变量名>  变量界的下/上松弛
for var in relax.getVars():
    if var.VarName.startswith(("ArtP_", "ArtN_")) and var.X > 1e-9:
        print(var.VarName, var.X)
```

`Model.feasRelaxS(relaxobjtype, minrelax, vrelax, crelax)` 这个签名是从 gurobipy 14.0 里 `inspect.signature` 读出来的；`ArtP_` / `ArtN_` / `ArtL_` / `ArtU_` 的命名规则出自官方文档 "Naming of the Variables and Constraints" 一节。**没有许可证，这段代码没跑过**，只核对了名字。

要按约束分别设惩罚（比如合同罚 10 倍），用完整版 `feasRelax(relaxobjtype, minrelax, vars, lbpen, ubpen, constrs, rhspen)`——`rhspen` 就是每条约束的权重，签名同样核对过。

### 10.4.2 COPT（已实跑）

COPT 的简化版接口只有两个开关，没有逐条惩罚（要逐条设惩罚得用 `feasRelaxN`，它要求把 vars/constrs 按矩阵对象传进去；本机只确认了这个方法存在，没展开验证）：

```python
model.feasRelaxS(True, True)      # vrelax, crelax
print(model.getAttr("HasFeasRelaxSol"), model.getAttr("FeasRelaxObj"))
for con in model.getConstrs():
    print(model.getInfo("RelaxLB", con), model.getInfo("RelaxUB", con))
```

**读结果有个口径陷阱（本机实测）：`RelaxLB` / `RelaxUB` 是"新界 − 原界"，不是"违反量"。** 松弛下界时 `RelaxLB` 是**负数**：

```
FeasRelaxMode=0（最小化违反量之和，L1）
  HasFeasRelaxSol=1 FeasRelaxObj=8
    ★ cap_B    原界 [-1e+30, 5] → [-1e+30, 8]   违反量 = 3
    ★ order_A  原界 [20, 1e+30] → [15, 1e+30]   违反量 = 5
```

`order_A` 报的是 `-5`，含义是"下界被降了 5"，不是"违反了 5"。写成 `abs()` 才对得上 `FeasRelaxObj = 8`。`writeRelax` 写出的 `.relax` 文件可以直接核对：

```
Maximize
   40 a + 50 b
Subject To
 cap_A: a <= 15
 cap_B: b <= 8
 order_A: a >= 15
 order_B: b >= 8
 shared: a + b <= 100
END
```

把六个 `FeasRelaxMode` 在同一个模型上扫一遍，答案差异很大（`code/ch10_infeasible/feasrelax_copt.py` 实跑）：

| mode | 含义 | `FeasRelaxObj` | 改动的约束 |
| :---: | :--- | ---: | :--- |
| 0 | 违反量之和 | 8 | `cap_B`(上界+3)、`order_A`(下界−5) |
| 1 | L1 最小前提下优化原目标 | 1200 | `cap_A`(上界+5)、`cap_B`(上界+3) |
| 2 | 违反条数 | 2 | `cap_A`(上界+5)、`cap_B`(上界+3) |
| 3 | L0 最小前提下优化原目标 | 5000 | `cap_B`(上界+95)、`order_A`(下界−20) |
| 4 | 违反量平方和 | 17 | 四条约束各改 2.5 / 1.5 |
| 5 | L2 最小前提下优化原目标 | 1025.29 | 四条约束各改约 2.5 / 1.5 |

三个要读出来的信息：

1. **mode 1/3/5 的 `FeasRelaxObj` 不再是违反量**，而是恢复原目标后的目标值（mode 1 的 1200 = $40 \times 20 + 50 \times 8$，mode 3 的 5000 = $50 \times 100$，都能对上）。同一个属性名在不同 mode 下含义不同，别混着比。
2. **mode 3 是"最危险"的那一个**：违反条数压到 2 之后（$a$ 一条、$b$ 一条，本来就躲不掉），它拿这两个名额去换利润——把 `cap_B` 放宽 95、让 $b$ 顶到 100，同时把 `order_A` 的下限降到 0。业务上这叫"为了一点收益把产能约束彻底放弃"，而这种方案在"条数最小"的量法下**完全合法**。
3. **`feasRelaxS` 不给你解向量**。原模型仍然不可行，`a.x` 会报 `INVALID`；想要"改完之后到底多少产量"，得把松弛量落回模型再解一次：

```python
repaired = build(env, 0)
for con in repaired.getConstrs():
    if con.name in delta:                     # delta 来自 RelaxLB / RelaxUB
        con.lb += delta[con.name][0]
        con.ub += delta[con.name][1]
repaired.solve()
```

实跑结果：目标值 1000，`a = 15`、`b = 8`。注意这和"最小改动点"（$a=15, b=5$）不是同一个点——松弛只保证改动最小，改完的可行域里再优化，解会跑到别处。要"改动最小的前提下利润最大"，请用 mode 1。

### 10.4.3 HiGHS：手工建弹性模型（已实跑）

HiGHS 没有 `feasRelax`，那就自己写。**这套写法同样适用于 SCIP（见 10.4.4）和任何支持线性建模的接口**，只是建变量和加约束的 API 不同。

```python
def build_elastic(weights):
    model = highspy.Highs()
    model.setOptionValue("output_flag", False)

    x = [model.addVariable(lb=0, name=name) for name in ("a", "b")]
    sp, sm = {}, {}
    for name, coefs, _sense, rhs in ROWS:
        sp[name] = model.addVariable(lb=0, name=f"sp_{name}")
        sm[name] = model.addVariable(lb=0, name=f"sm_{name}")
        expr = sum(coef * x[i] for i, coef in coefs.items())
        model.addConstr(expr + sp[name] - sm[name] == rhs, f"{name}_elastic")

    # 只有"真正构成违反"的那一侧进目标
    terms = []
    for name, _coefs, sense, _rhs in ROWS:
        weight = weights.get(name, 1.0)
        if sense == "L":
            terms.append(weight * sm[name])
        elif sense == "G":
            terms.append(weight * sp[name])
        else:
            terms.append(weight * (sp[name] + sm[name]))
    model.setObjective(sum(terms), highspy.ObjSense.kMinimize)
    return model, x, sp, sm
```

两处不显眼但必须写对：

- **只有构成违反的那一侧进目标。** `<=` 行只把 `sm` 放进目标，`>=` 行只放 `sp`。如果两边都放，求解器会发现"把 sp 和 sm 同时抬起来"能让等式成立，白白虚增目标值，模型照样"最优"但毫无意义。
- **用等式形式统一三种关系符。** 也可以保留 `<=` 只加一个松弛（`expr - s <= rhs`），但那样每个关系符要写一套分支，容易出错。

解出来之后，**违反量就是松弛变量的取值**，逐个打印即可：

```
等权（所有约束惩罚都是 1）
  加权违反量（目标值）= 8
  解：a = 15，b = 5
    cap_A    原右端项     15   违反量      0
    cap_B    原右端项      5   违反量      0
    order_A  原右端项     20   违反量      5  ★ 被改
    order_B  原右端项      8   违反量      3  ★ 被改
    shared   原右端项    100   违反量      0
  共改动 2 条约束
```

结果和 COPT 的 `FeasRelaxMode=0` 完全一致（总违反量 8，改 `order_A` 5、`cap_B` 3）——手工弹性模型和商用求解器的内置实现在这个问题上对得上，可以互相验证。

再换一组权重，答案就变了：

```
订单优先（order_* 的惩罚 = 10，cap_* 仍是 1）
  加权违反量（目标值）= 8
  解：a = 20，b = 8
    cap_A    原右端项     15   违反量      5  ★ 被改
    cap_B    原右端项      5   违反量      3  ★ 被改
    order_A  原右端项     20   违反量      0
    order_B  原右端项      8   违反量      0
    shared   原右端项    100   违反量      0
  共改动 2 条约束
```

"合同不能动"这件事，用权重表达就是一行 `{"order_A": 10.0, "order_B": 10.0}`。**权重不是数学参数，是业务决策**——把它写在配置文件里，别埋在代码里。

（本例两组方案的总违反量都是 8，只因权重不同就改了不同的约束。哪一组在业务上更能接受，求解器不会告诉你——这就是权重必须由人来定的原因。）

### 10.4.4 SCIP 的手工弹性模型

和 HiGHS 一模一样，只换三处 API：

```python
sp = model.addVar(f"sp_{name}", lb=0)
sm = model.addVar(f"sm_{name}", lb=0)
model.addCons(expr + sp - sm == rhs, name=f"{name}_elastic")
model.setObjective(sum(terms), "minimize")
```

SCIP 的 `setObjective(expr, sense)` 第二个参数是字符串 `"minimize"` / `"maximize"`（不是枚举），这点和 HiGHS 的 `highspy.ObjSense.kMinimize` 不同。

## 10.5 IIS 和 feasRelax 怎么选

| 你想知道 | 用哪个 | 为什么 |
| :--- | :--- | :--- |
| 到底哪几条约束打架 | IIS | 输出是"成员清单"，可读性强，还能落成 `.iis`/`.ilp` 交给别人 |
| 业务上最少改多少能跑 | 可行性松弛 | 输出是"每条改多少 + 总代价"，可以直接拿去谈条件 |
| 数据是不是录错了 | 都不用，先自查 | 见 10.6 的建模错误表 |
| 只能修一处，修哪个 | IIS（迭代） | 修一条、再算、看下一个 IIS |

**关于 `minrelax`（Gurobi）/ mode 1·3·5（COPT）**：它**不是**"再求一次 IIS"。官方文档的描述是——先按选定的量法解一次松弛，得到最小违反量；然后把这个值作为一条名叫 `feasobj` 的约束加回模型，恢复原目标，再解一次。所以它回答的是"**在改动最小的前提下，我的原目标最好能做到多少**"，输出仍然是一个解，不是冲突集。

这两步的顺序很重要：先求最小违反量，再在这个前提下优化原目标。反过来（先优化目标、再看违反量）会得到一个完全没有意义的结果。

## 10.6 实操清单

### 第一步：看状态码，别看数值

| 现象 | Gurobi | COPT | HiGHS | 含义 |
| :--- | :--- | :--- | :--- | :--- |
| 不可行 | `Status == 3` | `status == 2`（`COPT.INFEASIBLE`） | `kInfeasible` | 先查 IIS |
| 不可行或无界 | `Status == 4` | `status == 4`（`COPT.INF_OR_UNB`） | `kUnboundedOrInfeasible` | 求解器没区分，见下 |

三条实操要点：

1. **Gurobi 的 4 必须再解一次**：`model.Params.DualReductions = 0` 之后重新 `optimize()`，才能把 4 拆成 3（不可行）或 5（无界）。不关对偶归约，后面 `computeIIS()` 也没意义。
2. **COPT 的常数名是 `COPT.INF_OR_UNB`**，不是 `INF_OR_UNBD`。本机实测 `getattr(COPT, "INF_OR_UNBD")` 直接 `AttributeError`——这一点和第 9 章 9.5 节那张表里的"status == 4"要对着看，别按 Gurobi 的拼法写。
3. **到时限不等于无解**：`kTimeLimit` / `Status == 9` 时可能已经有可行解（`SolCount > 0`），此时去算 IIS 会得到莫名其妙的结果。先确认真的不可行。

### 第二步：建模自查（比 IIS 快十倍）

不可行的模型里，很大一部分根本不是"业务冲突"，而是笔误：

| 错误 | 症状 | 正确做法 |
| :--- | :--- | :--- |
| 漏了需求满足约束 | 解出来需求没满足，或模型直接不可行 | 逐条核对"每条业务规则是否都有对应约束" |
| 上下界写反 | `lb > ub`，模型一建好就不可行 | 断言 `lb <= ub`，或干脆不写冗余界 |
| 用 `==` 表达"约等于" | 永远不可行（第 9 章 9.6 节） | 改区间约束 `>= lo` / `<= hi` |
| 单位不一致 | 约束间量级差 $10^3$ 以上，或直接冲突（吨 vs 千克） | 建数据时就统一单位，别在约束里换算 |
| 集合为空导致空约束 | 求和项为空 → `0 <= -5` 这种恒不成立的行 | 加约束前 `if not items: continue`，并打日志 |
| big-M 给小了 | 本来可行的组合被 M 卡死 | 用问题自身算出的上界（第 4 章） |

表里第 5 行那个"空约束"值得单独说：`sum(...) <= b` 在集合为空时退化成 `0 <= b`，只要 $b < 0$ 就凭空多一条不可行约束。这类 bug 在按日期/按省份循环建模的代码里极其常见，症状是"大部分日期能跑，个别日期无解"。

### 第三步：IIS → 修 → 再解，循环到可行

```text
1. solve()            → 看状态码
2. computeIIS()       → 看成员（约束 + 变量界）
3. 修一条             → 改右端项 / 放宽界 / 删掉写错的约束
4. 回到 1            → 还有 IIS 就继续，别只做一轮
```

### 第四步：需要"最少改多少"时才上松弛

```text
1. 先想清楚权重 w_r 的业务含义（哪条绝对不能动）
2. 选量法：L1 看总量、L2 怕某一处被改太狠、L0 看条数
3. 有内置接口就用（Gurobi feasRelax / COPT feasRelax），没有就手工建弹性模型
4. 把每条约束的违反量打印出来，逐条和业务方确认
```
